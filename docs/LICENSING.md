## 2. 왜 MIT인가

| 후보 | 장점 | 단점 | 판단 |
|---|---|---|---|
| **MIT** | 가장 짧고 널리 알려짐. 기업 내부 코드에 로거로 넣을 때 검토 부담이 가장 적음. Python 로깅 생태계(structlog, loguru 등)에서 흔히 쓰는 라이선스와 같은 계열 | 특허 조항이 없음 | **채택** |
| Apache-2.0 | 명시적 특허 허여, 기여자 특허 보호 | 문서가 길고, NOTICE 파일 처리 의무가 있음 | 정규식과 문자표 위주인 도구라 특허 위험이 낮아 불필요하다고 판단 |
| MPL-2.0 / LGPL | 수정본 공개를 강제 | 로거 포맷터처럼 코드 깊숙이 들어가는 라이브러리에는 도입 장벽 | 제외 |
| GPL / AGPL | 강한 카피레프트 | 기업 채택이 사실상 막힘 | 제외 |

이 프로젝트의 성패는 **"로거 설정 한 줄로 바로 넣을 수 있는가"** 에 달려 있습니다. 그래서 라이선스 검토 비용이 가장 낮은 MIT를 고릅니다.

## 3. 의존성과 데이터 허용 목록

| 분류 | 허용 라이선스 (SPDX) |
|---|---|
| 런타임 선택 의존성 | `MIT`, `BSD-2-Clause`, `BSD-3-Clause`, `Apache-2.0`, `ISC`, `PSF-2.0`, `CNRI-Python` |
| 포함(vendoring) 데이터 | `Unicode-3.0`, `MIT`, `CC0-1.0` |
| 금지 | `GPL-*`, `AGPL-*`, `LGPL-*`, `SSPL-*`, 라이선스가 명시되지 않은 모든 것 |

- 새 의존성이나 데이터를 추가하는 PR에는 SPDX 식별자와 확인 날짜를 적고 [THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md) 를 갱신합니다.
- CI에서 `pip-licenses` 로 허용 목록을 검사합니다 (v0.2).

## 4. 규칙 데이터의 출처 정책

규칙(문자표, 상투 표현 목록)은 이 프로젝트의 핵심 자산이라 출처를 엄격히 관리합니다.

1. **직접 작성**이 기본입니다. Unicode 표준 데이터에서 파생된 문자표는 파생 스크립트와 Unicode 버전을 함께 커밋합니다.
2. **다른 프로젝트의 규칙 목록을 복사하지 않습니다.** [RESEARCH.md](RESEARCH.md) 5장의 도구들(slop-chop, unslopify, unslop, demdash 등)은 아이디어 참고만 하고, 목록이나 문구를 가져오려면 해당 저장소의 라이선스를 먼저 확인해 허용 목록에 있을 때만 출처를 남기고 가져옵니다.
3. Ruff의 confusables 데이터는 VS Code의 ambiguous 문자표에서 왔다고 문서화되어 있습니다. 이 데이터를 쓰려면 VS Code 저장소의 라이선스 원문을 확인하고 THIRD_PARTY_NOTICES 에 추가합니다.

## 5. AI 도구로 만든 기여

이 프로젝트는 AI가 만든 흔적을 치우는 도구이지만, AI 도구로 작성한 기여 자체를 막지는 않습니다.

- 기여자는 DCO 서명으로 **자신이 제출할 권리가 있음을 보증**합니다. AI 도구가 만든 코드도 같습니다.
- 다른 프로젝트의 코드를 AI가 그대로 재현했을 가능성이 있는 큰 덩어리(특히 규칙 목록)는 리뷰어가 출처를 물어볼 수 있습니다.
- 이 저장소의 커밋 메시지, 문서, 로그 문자열은 이 도구 자체의 린터(`check --all`)를 통과해야 합니다 (dogfooding).

## 6. 상표와 이름

- 프로젝트 이름과 로고는 MIT 라이선스의 대상이 아닙니다. 포크는 자유롭지만, 공식 배포판으로 오해될 수 있는 같은 이름 사용은 피해 달라고 [GOVERNANCE.md](../GOVERNANCE.md) 에서 요청합니다.
- 상표 사전 점검은 메인테이너가 수행했으며, 결과는 상표 출원 이후 공개 여부를 정합니다.
